# 붕괴: 스타레일 유물 점수 계산기 개발 계획서

## 1. 문서 목적

이 문서는 프로젝트의 개발 계획, 구현 과정, 사용법, 테스트 결과, 문제 해결 과정, 실사용 후기를 한곳에 누적하기 위한 기준 문서다. 앞으로 기능을 추가하거나 수정할 때마다 작업 내용과 검증 결과를 이 문서에 기록한다.

## 2. 프로젝트 개요

- 주제: 붕괴: 스타레일 유물(성유물) 점수 계산기
- 목표: 사용자가 유물의 주옵션과 부옵션을 입력하면 선택한 캐릭터 또는 육성 방향에 맞는 점수, 등급, 세부 평가를 즉시 확인할 수 있는 웹 앱을 만든다.
- 대상 사용자: 보유 유물의 강화 가치와 캐릭터별 적합도를 빠르게 비교하고 싶은 플레이어
- 사용 기술: C#, .NET 10, Blazor WebAssembly, ASP.NET Core Web API, Redis, xUnit, Docker Compose
- 배포 형태: 설치 없이 브라우저에서 사용하는 웹 앱. Blazor 클라이언트와 ASP.NET Core API를 배포하고, API가 Redis에 최근 계산 기록과 사용 통계를 저장한다.

## 3. 핵심 개발 원칙

1. 계산식과 화면 표시 코드를 분리한다.
2. 스탯 이름, 가중치, 등급 기준은 데이터에서 관리하고 화면 코드에 중복 저장하지 않는다.
3. 사용자가 점수의 근거를 확인할 수 있도록 스탯별 기여도를 함께 보여준다.
4. 잘못된 입력은 조용히 무시하지 않고 입력 위치와 해결 방법을 표시한다.
5. 초기 버전은 수동 입력에 집중하고, 이미지 인식 같은 큰 기능은 기본 버전 완성 후 검토한다.
6. 모든 작업은 코드 변경, 검증 결과, 문제와 해결 방법까지 이 문서에 기록한 뒤 완료로 처리한다.

## 4. 구현 범위

### 4.1 필수 기능(MVP)

- 유물 부위, 강화 단계, 주옵션을 선택한다.
- 최대 4개의 부옵션 종류와 수치를 입력한다.
- 치명타, 공격력, HP, 방어력, 격파, 효과 명중·속도 서포터 평가 프로필을 선택한다.
- 입력값을 기준으로 총점과 등급을 계산한다.
- 스탯별 가중치와 점수 기여도를 표시한다.
- 필수값 누락, 중복 스탯, 허용 범위를 벗어난 값에 대한 오류를 표시한다.
- 모바일과 데스크톱에서 모두 사용할 수 있는 반응형 화면을 제공한다.
- 계산 결과와 마지막 입력을 브라우저에 저장하여 새로고침 후 복원한다.
- 입력 초기화 기능을 제공한다.

### 4.2 완성도를 높이는 후속 기능

- 캐릭터별 추천 평가 프로필
- 여러 유물의 점수 비교와 정렬
- 결과를 이미지 또는 텍스트로 공유하는 기능
- 다크 모드와 키보드 접근성 개선
- 사용자 피드백을 반영한 점수 기준 보정

후속 기능은 MVP의 계산 정확성, 테스트, 배포가 완료된 뒤 우선순위를 다시 판단한다.

## 5. 점수 계산 설계

점수는 각 부옵션의 수치와 평가 프로필별 가중치를 사용해 계산한다.

```text
스탯 기여도 = 입력 수치 / 해당 스탯의 기준 수치 × 프로필 가중치
총점 = 모든 스탯 기여도의 합을 표시용 점수 범위로 환산
등급 = 검증된 구간에 따라 S, A, B, C 등으로 표시
```

- 기준 수치와 가중치는 UI와 분리된 C# Domain 코드에서 한 번만 관리한다.
- 치명타 확률처럼 표시 단위가 퍼센트인 값과 속도처럼 고정 수치인 값을 구분한다.
- 주옵션은 유물의 사용 가능성을 설명하는 별도 평가에 활용하고, 부옵션 점수와 혼합할 경우 계산 근거를 명시한다.
- 정확한 기준 수치, 가중치, 등급 구간은 구현 전에 게임 데이터와 대표적인 계산 방식을 조사하고 샘플 유물로 검증한 뒤 확정한다.
- 결과 화면에는 총점만 보여주지 않고 적용된 프로필, 가중치, 스탯별 기여도를 함께 표시한다.

## 6. 화면 구성

1. 헤더: 프로젝트 이름과 간단한 사용 설명
2. 평가 기준 선택 영역: 캐릭터 또는 육성 프로필 선택
3. 유물 입력 영역: 부위, 강화 단계, 주옵션, 부옵션 입력
4. 결과 영역: 총점, 등급, 적용 프로필, 스탯별 점수 내역
5. 도움말 영역: 계산 기준, 주의사항, 데이터 갱신일
6. 푸터: GitHub 저장소, 버전, 피드백 경로

한 화면에서 입력과 결과를 확인할 수 있게 구성하며, 모바일에서는 입력 영역 아래에 결과가 이어지도록 배치한다.

## 7. 예상 코드 구조

```text
src/
  ArtifactGrade.Domain/  점수 계산, 입력 검증, 스탯 기준
  ArtifactGrade.Api/     계산 API와 Redis 저장
  ArtifactGrade.Client/  Blazor WebAssembly UI
tests/
  ArtifactGrade.Domain.Tests/  계산 및 검증 테스트
docs/
  DEVELOPMENT_PLAN.md
README.md
docker-compose.yml
```

계산기는 UI에 의존하지 않는 순수 함수로 만들고, UI는 입력을 전달하고 결과를 표시하는 역할만 맡는다.

## 8. 단계별 개발 계획

### 1단계: 요구사항과 계산 기준 확정

- 게임 내 유물 부위, 주옵션, 부옵션, 강화 규칙을 정리한다.
- 평가 프로필별 유효 스탯과 가중치를 정한다.
- 샘플 유물과 예상 점수를 작성해 계산식 검증 기준으로 사용한다.
- 완료 조건: 같은 입력에 항상 같은 결과가 나오며 계산 과정을 손으로 재현할 수 있다.

### 2단계: C# 프로젝트 기반과 기본 화면 구현

- .NET 10, Blazor WebAssembly, ASP.NET Core 개발 환경을 구성한다.
- 입력 폼과 결과 카드의 반응형 화면을 구현한다.
- 접근 가능한 라벨, 키보드 입력, 명확한 오류 문구를 적용한다.
- 완료 조건: PC와 모바일 화면에서 모든 입력 항목을 불편 없이 사용할 수 있다.

### 3단계: 계산 및 검증 로직 구현

- 스탯 데이터, 프로필 가중치, 등급 기준을 정의한다.
- 점수 계산 순수 함수와 입력 검증을 구현한다.
- 스탯별 기여도와 총점이 일치하도록 결과를 연결한다.
- 완료 조건: 정상값, 경계값, 잘못된 값에 대한 자동 테스트를 통과한다.

### 4단계: 사용자 편의 기능 구현

- 마지막 입력과 설정을 브라우저에 저장한다.
- 초기화와 결과 공유 기능을 추가한다.
- Redis에 최근 계산 기록과 사용 통계를 저장하고, Redis 장애 시 계산 결과와 저장 실패 안내를 함께 반환한다.
- 빈 화면, 오류, 저장 데이터 손상 상황을 처리한다.
- 완료 조건: 새로고침과 재방문 후에도 정상 동작하고 잘못된 저장값은 사용자에게 알린다.

### 5단계: 품질 점검과 배포

- 단위 테스트, 사용자 흐름 테스트, 프로덕션 빌드를 실행한다.
- Chrome, Edge 및 모바일 화면 크기에서 직접 확인한다.
- GitHub Actions에서 테스트와 빌드를 자동화한다.
- Blazor 클라이언트, ASP.NET Core API, Redis를 지원하는 환경에 배포한다. GitHub Pages는 서버와 Redis를 실행할 수 없으므로 전체 서비스의 단독 배포 대상으로 사용하지 않는다.
- README에 소개, 설치법, 실행법, 계산 기준, 배포 주소를 정리한다.
- 완료 조건: 새 환경에서 문서만 보고 실행할 수 있고 공개 주소에서 오류 없이 동작한다.

### 6단계: 실사용과 공개

- 실제 보유 유물을 최소 10개 입력해 점수와 사용성을 확인한다.
- 장점, 단점, 불편한 점, 개선 우선순위를 실사용 후기로 작성한다.
- 스크린샷 또는 짧은 시연 자료와 함께 개발 블로그나 개인 SNS에 게시한다.
- GitHub 저장소의 설명, README, 라이선스, 배포 링크를 최종 점검한다.
- 완료 조건: 후기 및 게시물 링크가 문서와 README에 기록되어 있다.

## 9. 테스트 계획

- 계산 테스트: 각 스탯, 가중치 0, 최대·최소값, 반올림, 등급 경계

### 2026-09-13 / 초기 개발 계획 수립

- 목적: 빈 저장소에서 프로젝트 범위와 완료 기준을 명확히 정한다.

- 결정과 이유: 설치 장벽이 낮고 GitHub Pages 배포가 쉬운 React, TypeScript, Vite 기반 정적 웹 앱을 제안했다. 첫 버전은 계산의 정확성과 설명 가능성을 우선하여 수동 입력형으로 제한했다.
- 검증 방법 및 결과: 저장소에는 프로젝트 설명만 있는 `README.md` 외에 구현 파일이 없음을 확인했다. 계획 문서에 기능, 구조, 단계, 테스트, 평가 항목을 연결했다.
- 문제와 해결: 정확한 점수 기준은 아직 검증되지 않았으므로 임의의 수치를 확정하지 않고 1단계 조사와 샘플 검증 대상으로 남겼다.

### 2026-09-13 / 구현 언어 변경 및 Redis 도입 결정

- 목적: 사용자 요청에 맞춰 전체 구현 언어를 C#으로 통일하고 Redis 활용 범위를 정한다.
- 변경 내용 및 파일: 기술 구성을 C#, .NET 10, Blazor WebAssembly, ASP.NET Core Web API, Redis, xUnit으로 변경했다. 앞서 준비한 TypeScript 초기 설정과 테스트 파일은 실제 구현 전에 제거했다.
- 결정과 이유: 브라우저 UI는 Blazor WebAssembly로, 계산 및 저장은 ASP.NET Core API로 구현한다. Redis는 최근 계산 기록과 사용 통계를 저장한다.
- 검증 방법 및 결과: 로컬 환경에 .NET SDK 10.0.400이 설치되어 있고 Blazor, Web API, xUnit 템플릿을 사용할 수 있음을 확인했다.
- 문제와 해결: Redis는 정적 사이트에서 직접 사용할 수 없으므로 API 서버를 추가하고, GitHub Pages 단독 배포 계획을 서버와 Redis를 지원하는 배포 방식으로 변경했다.

## 13. 트러블슈팅

### NuGet.Config 접근 거부 및 복원 지연

- 증상: `dotnet restore`가 사용자 프로필의 `NuGet.Config`에 접근하지 못하거나 NuGet.org 응답을 기다리다 타임아웃됐다.
- 원인: 샌드박스에서 사용자 프로필 설정 파일 읽기가 제한되었고 첫 패키지 다운로드가 지연됐다.
- 해결: 저장소 루트에 필요한 소스만 선언한 `NuGet.Config`를 추가하고 `--configfile NuGet.Config`로 복원했다. 확보된 로컬 패키지는 `--ignore-failed-sources`로 사용할 수 있다.
- 재발 방지: README와 Dockerfile, CI가 모두 저장소의 `NuGet.Config`를 명시적으로 사용한다.

### API가 빈 응답으로 연결을 종료함

- 증상: 서버가 실행 중인데 `/api/scores` 요청은 빈 응답으로 끝났다.
- 원인: Windows Event Log 로깅 공급자가 권한 없는 이벤트 로그에 HTTPS 경고를 기록하려다 예외를 발생시켰다.
- 해결: API 로깅 공급자를 Console로 제한하고, HTTPS 종료는 운영 리버스 프록시가 담당하도록 애플리케이션의 강제 리디렉션을 제거했다.
- 재발 방지: API 스모크 테스트로 실제 HTTP 응답을 확인한다.

### 화면에 입력했지만 부옵션이 없다고 표시됨

- 증상: 숫자 4개가 화면에 보이는데도 부옵션 개수 오류가 반환됐다.
- 원인: 기본 바인딩이 `change` 이벤트에서 동작해 계산 버튼을 누른 시점에 마지막 입력이 C# 상태에 반영되지 않았다.
- 해결: 숫자 입력을 `oninput` 이벤트에 바인딩했다.
- 재발 방지: 브라우저에서 실제 입력·클릭 흐름을 검증한다.

### API 응답 뒤 연결 실패 문구가 표시됨

- 증상: API는 정상 응답했지만 클라이언트가 연결 실패로 표시했다.
- 원인: API는 enum을 문자열로 보냈고 클라이언트는 기본 숫자 enum 형식으로 읽었다.
- 해결: 양쪽에 `JsonStringEnumConverter`를 적용하고 연결 오류와 JSON 오류 메시지를 분리했다.
- 재발 방지: API 스모크 테스트와 브라우저 계산 테스트를 함께 실행한다.

### Redis가 없는 개발 환경

- 증상: 점수는 계산되지만 Redis 저장 경고가 표시된다.
- 원인: 현재 검증 환경에 Docker와 `redis-server`가 설치되어 있지 않다.
- 해결: 저장 실패를 숨기지 않고 결과에 경고를 포함했다. Docker가 있는 환경에서는 `docker compose up --build`로 Redis까지 실행한다.
- 재발 방지: 외부 배포 전 `/api/health`가 `healthy`, `redis=connected`를 반환하는지 확인한다.

### Release 빌드와 테스트 동시 실행 시 DLL 잠금

- 증상: `ArtifactGrade.Domain.dll`을 `VBCSCompiler`가 사용 중이라는 `CS2012` 오류가 발생했다.
- 원인: 같은 프로젝트를 참조하는 전체 빌드와 테스트 빌드를 동시에 실행해 동일한 `obj/Release` 파일에 쓰기를 시도했다.
- 해결: 전체 Release 빌드를 먼저 끝낸 뒤 `dotnet test --no-build`를 순차 실행했다.
- 재발 방지: 동일 구성의 빌드와 테스트는 병렬 실행하지 않고 CI와 로컬에서 순서를 고정한다.

### Windows에서 API 스모크 테스트 스크립트 실행 차단

- 증상: API는 정상 기동했지만 `api-smoke.ps1`이 `PSSecurityException`으로 실행되지 않았다.
- 원인: 현재 Windows 사용자의 PowerShell 실행 정책이 로컬 스크립트 실행을 허용하지 않았다.
- 해결: `powershell -NoProfile -ExecutionPolicy Bypass -File tests/api-smoke.ps1`로 해당 프로세스에만 우회 정책을 적용했다.
- 재발 방지: README의 스모크 테스트 명령에 프로세스 단위 실행 정책 옵션을 포함한다.

### 2026-09-14 / UID 및 Scanner JSON 자동 가져오기 구현

- 목적: 유물의 강화 단계, 부위, 주옵션과 부옵션을 하나씩 입력하지 않아도 공개 프로필 또는 스캐너 파일에서 계산할 수 있게 한다.

- 결정과 이유: UID 경로는 설치가 없지만 공개 장착 유물만 제공한다. 전체 인벤토리는 HSR Scanner 버전 4 호환 JSON으로 보완한다. HoYoLAB 로그인 쿠키 수집과 애플리케이션 내 패킷 캡처는 구현하지 않았다.
- 입력 보호: UID 숫자 9자리 검증과 호출자 IP별 분당 10회 호출 제한, JSON 최대 10MB, Scanner 버전 4 확인, 5성 필터, 지원하지 않는 스탯 경고, 일괄 요청 최대 300개와 null 항목 거부를 적용했다. 잘못된 UID는 호출 제한 횟수에 포함하지 않는다. 클라이언트는 300개씩 나누어 전체 목록을 계산한다.
- TDD 결과: MiHoMo 필드 변환, Redis 캐시 재사용, 지원하지 않는 유물 경고, Scanner 캐릭터·부위·주옵션·부옵션 변환, 잘못된 문서 오류 정규화, 일괄 점수 계산, 5성이 아닌 유물 거부와 외부 소수 오차 허용 테스트를 실패부터 확인한 뒤 구현했다.
- 실제 API 검증: Docker와 Redis 없이 MiHoMo 예제 UID `100000999`에서 5성 장착 유물 42개를 가져왔다. Scanner 샘플은 Bronya 장착, Hands, FlatAttack으로 변환됐고 일괄 계산은 40점 B등급을 반환했다.
- 브라우저 검증: UID 42개 표시, 선택 유물 입력 적용, 42개 전체 계산과 내림차순 정렬을 확인했다. 390px 화면의 문서 너비와 화면 너비가 같아 가로 넘침이 없었고 브라우저 오류 로그는 0개였다.
- 문제와 해결 1: 실행 중인 API가 변경 전 빌드여서 `/api/scores/batch`가 404를 반환했다. API를 다시 빌드·재시작한 뒤 정상 응답을 확인했다.
- 문제와 해결 2: `127.0.0.1`로 연 클라이언트는 개발 CORS 허용 주소인 `localhost`와 출처가 달라 API 호출이 차단됐다. README에 적힌 `http://localhost:5111`로 통일해 검증했다.
- 문제와 해결 3: MiHoMo의 정확한 실수 값이 로컬 최고 증가량 상수를 약 `0.00004` 초과하는 경우가 있었다. 실제로 가능한 값을 거부하지 않도록 최대치 검증에 `0.001` 허용 오차를 추가하고 큰 초과값을 거부하는 기존 테스트는 유지했다.
- 문제와 해결 4: Windows PowerShell 5.1이 BOM 없는 UTF-8 테스트 스크립트의 한글 문자열을 잘못 해석했다. 스모크 테스트 메시지를 ASCII로 바꿔 실행 환경에 따른 파싱 오류를 제거했다.
- 리뷰와 수정: 명세·코드 품질 두 관점으로 변경분을 검토했다. 필수 JSON 속성 누락 시 500이 되던 문제, UID 외부 호출 제한 부재, 일괄 계산 중 프로필·가져오기 상태가 바뀌는 문제, 일괄 목록의 null 항목 문제를 수정했다. 재검토에서 일괄 검증 오류 상세 누락, 전체 사용자가 공유하던 호출 제한, Docker 없는 실행 안내의 모호함을 추가로 찾아 수정했다. 일괄 계산은 시작 시 프로필과 목록을 스냅샷으로 고정한다.
- 프록시 처리: Docker 배포에서는 Nginx 주소만 호출자로 인식될 수 있어 신뢰된 프록시 전달 헤더 처리를 호출 제한보다 앞에 추가했다. Compose는 전용 `172.30.0.0/24` 네트워크만 신뢰하고 API 호스트 포트를 `127.0.0.1`에 바인딩해 임의 외부 요청이 전달 헤더를 위조하지 못하게 했다. 로컬 신뢰 프록시 테스트에서 첫 IP는 10회 200 후 429가 됐지만 두 번째 IP의 첫 요청은 200으로 유지되어 제한이 분리됨을 확인했다.
- 최종 검증: 전체 xUnit 테스트 19개가 통과했고 Release 빌드는 경고 0개, 오류 0개였다. Docker 없이 Scanner 가져오기·40점 일괄 계산을 다시 통과했다. UID 호출 제한은 로컬 MiHoMo 대역 서버에서 검증했다. 잘못된 UID 11회는 모두 400이었고, 이어서 유효한 UID를 11회 보내 같은 호출자 IP의 앞 10회는 200, 마지막 요청은 JSON 안내와 함께 429가 되는 것을 확인했다.

- 최종 검증: 수정 후 실행 파일을 다시 실행했을 때 API와 클라이언트를 모두 기존 프로세스로 인식하고 중복 실행 없이 브라우저만 열었다. 전체 xUnit 테스트 20개가 통과했고 Release 빌드는 경고 0개, 오류 0개였다.

- 변경 내용 및 파일: `Home.razor`의 유물 옵션 요약을 `RelicStatSummary`로 정리해 주옵션 이름과 단위를 먼저 표시하고 기존 부옵션 수치를 이어서 표시했다. 데이터 계약과 점수 계산 방식은 변경하지 않았다. `README.md`와 `BLOG_POST_DRAFT.md`에도 표시 방식과 사용법을 추가했다.
- 표시 형식: `주옵션 {이름}{단위} · 부옵션 {이름 수치 단위} · …` 형식을 사용한다. 예를 들어 공격력 백분율 몸통 유물은 `주옵션 공격력% · 부옵션 치명타 확률 6.48% · 치명타 피해 12.96% · 속도 5.2 · 공격력 21.17`로 보인다.
- 검증 방법: 먼저 Client Release 빌드로 Razor와 C# 컴파일을 확인했다. 이후 MiHoMo 계약과 같은 로컬 응답에서 Jingliu의 5성 몸통 유물을 불러오고 `전체 점수 계산`을 실행해 주옵션이 부옵션 앞에 표시되는지 브라우저 DOM에서 확인했다. 브라우저 오류·경고 로그는 0개였다.
- 검증 중 문제와 해결: 검증 환경에서 외부 MiHoMo 연결이 제한되어 공개 UID 요청이 실패했다. 테스트에서 사용 중인 동일 계약의 로컬 MiHoMo 대역 응답으로 전환해 화면부터 API 변환까지 같은 사용자 흐름을 검증했다. 짧은 검증용 서버 실행 시간이 끝나 연결이 끊긴 경우에는 제한 시간을 늘린 독립 프로세스로 다시 실행했다.
- 리뷰와 수정: 처음에는 선택한 부위의 주옵션 목록에서 이름을 찾았다. 형식이 잘못된 Scanner 파일이 부위와 맞지 않는 주옵션 조합을 만들면 점수 검증 결과를 표시하기 전에 화면 렌더링이 실패할 수 있어, 알려진 전체 주옵션 사전에서 표시 이름을 찾도록 분리했다. 부위·주옵션 조합 오류는 기존 점수 검증이 `계산 불가`로 안내한다.
- 최종 검증: 전체 xUnit 테스트 20개가 통과했고 Release 빌드는 경고 0개, 오류 0개였다. 코드 포맷 검사도 변경 없이 통과했다.
- 사용법: UID 또는 Scanner JSON으로 유물을 불러오고 `전체 점수 계산`을 누른다. 캐릭터별 점수 목록에서 유물 이름 아래의 `주옵션`과 `부옵션` 요약을 확인한다.
