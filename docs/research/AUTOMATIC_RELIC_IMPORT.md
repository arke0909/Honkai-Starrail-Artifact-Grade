# 유물 정보 자동 가져오기 기술 조사

- 조사일: 2026-09-14
- 대상: 붕괴: 스타레일 유물 점수 계산기
- 목적: 사용자가 유물의 주옵션과 부옵션을 하나씩 입력하지 않고 점수 계산에 필요한 데이터를 가져오는 방법을 결정한다.

## 결론

자동 가져오기는 가능하다. 다만 공개 UID 조회만으로 계정의 전체 유물 가방을 가져오는 방식은 확인되지 않았다. 가장 현실적인 구성은 다음 두 경로를 함께 제공하는 것이다.

1. **UID 불러오기**: 설치 없이 빠르게 사용할 수 있지만 공개 프로필에 전시한 캐릭터의 장착 유물만 가져온다.
2. **스캐너 JSON 불러오기**: 별도 스캐너 실행이 필요하지만 전체 유물 인벤토리를 한 번에 가져올 수 있다.

스크린샷 OCR은 보조 기능으로 고려할 수 있지만 인식 오류와 숨겨진 속도 소수점 문제 때문에 우선순위가 낮다. HoYoLAB 로그인 세션이나 쿠키를 애플리케이션이 직접 수집하는 방식은 보안과 유지보수 위험 때문에 채택하지 않는다.

## 확인된 사실

| 방식 | 가져오는 범위 | 사용자 작업 | 확인된 제약 |
|---|---|---|---|
| 공개 UID 조회 | 공개 프로필 캐릭터의 장착 유물 | UID 입력 및 게임 내 프로필 공개 | Fribbels의 프로필 가져오기는 전시 캐릭터 최대 8명의 유물로 제한된다. |
| HSR Scanner JSON | 전체 유물 인벤토리와 캐릭터 정보 | 스캐너 실행 후 JSON 업로드 | OCR 방식이라 5~10분이 걸릴 수 있고 숨겨진 속도 소수점은 복원하지 못한다. 영어 UI와 16:9 화면이 필요하다. |
| Reliquary Archiver JSON/WebSocket | 전체 유물 인벤토리와 캐릭터 정보 | 패킷 캡처 도구 실행 후 JSON 업로드 또는 실시간 전송 | 빠르고 숨겨진 속도 소수점이 정확하지만 네트워크 캡처 드라이버와 별도 프로그램이 필요하다. |
| HoYoLAB 응답 가져오기 | 장착 유물 중심 | 로그인한 브라우저의 개발자 도구에서 응답 복사 | 인증된 세션을 전제로 하고 수동 단계가 남는다. |
| 스크린샷 OCR | 촬영한 유물 | 유물 화면 캡처 및 이미지 업로드 | 한 장씩 처리해야 하며 OCR 오인식 검수가 필요하다. 숨겨진 속도 소수점은 알 수 없다. |

MiHoMo는 `GET /sr_info_parsed/{uid}`에서 캐릭터별 유물 ID, 세트, 등급, 강화 단계, 주옵션과 부옵션 값을 포함한 공개 플레이어 데이터를 제공한다. 이 API를 UID 불러오기의 서버 측 데이터 공급원 후보로 사용한다. 공개 프로필 범위 제한은 Fribbels가 문서화한 프로필 가져오기 제약을 기준으로 판단한 것이다.

## 권장 구현안

### 1단계: UID 불러오기

현재 C# 구조에 다음 흐름을 추가한다.

```text
Blazor Client
  -> UID 입력
ASP.NET Core API
  -> UID 형식 검증
  -> MiHoMo 공개 프로필 API 조회
  -> 외부 유물 데이터를 ScoreRequest 형식으로 변환
  -> Redis에 짧은 기간 캐시
Blazor Client
  -> 불러온 유물 목록에서 선택
  -> 기존 점수 계산 실행
```

- 브라우저가 외부 서비스를 직접 호출하지 않고 ASP.NET Core API가 `HttpClient`로 조회한다.
- 외부 API 오류, 비공개 프로필, 존재하지 않는 UID, 호출 제한을 서로 다른 안내 문구로 표시한다.
- Redis는 원본 데이터베이스가 아니라 외부 조회를 줄이는 캐시로만 사용한다.
- 캐시 키에는 UID 원문 대신 해시를 사용하고 만료 시간을 둔다.
- 가져온 유물의 세트, 부위, 주옵션, 부옵션을 기존 도메인 enum과 요청 모델에 매핑한다.

장점은 별도 설치 없이 UID 한 번만 입력하면 된다는 점이다. 단점은 전체 가방이 아니라 공개 프로필에 장착·전시된 유물만 다룬다는 점이다.

### 2단계: 스캐너 JSON 불러오기

전체 인벤토리가 필요한 사용자를 위해 HSR Scanner 및 Reliquary Archiver 형식의 JSON 업로드를 지원한다.

- 업로드 파일 크기, JSON 스키마 버전, 필수 필드와 숫자 범위를 검증한다.
- 두 도구가 사용하는 내보내기 형식을 각각 어댑터에서 현재 도메인 모델로 변환한다.
- 업로드한 원본 JSON은 기본적으로 서버에 영구 보관하지 않는다.
- 여러 유물을 목록으로 보여주고 일괄 점수 계산과 정렬을 제공한다.
- 이름과 ID 매핑 자료가 필요하면 HSR Scanner가 사용하는 HSR-Data 형식을 참고한다.

### 3단계: 스크린샷 OCR(선택)

별도 프로그램 설치를 원하지 않는 사용자를 위한 보조 경로다. 이미지 한 장에서 한 유물을 읽고, 인식 결과를 사용자가 확인한 뒤 계산하도록 설계한다. OCR 결과를 곧바로 확정하지 않고 수정 가능한 미리보기를 두어야 한다.

## 채택하지 않는 기본 경로

### HoYoLAB 로그인·쿠키 수집

Fribbels의 HoYoLAB 가져오기 절차도 로그인한 브라우저의 개발자 도구에서 API 응답을 복사하도록 안내한다. HoYoLAB 이용약관은 계정 정보의 보안과 기밀 유지 책임을 사용자에게 둔다. 현재 프로젝트가 사용자의 로그인 쿠키나 세션 토큰을 직접 받으면 계정 보안 부담이 커지고 외부 응답 형식 변경에도 취약해진다. 따라서 기본 기능에서는 로그인 정보나 쿠키를 수집하지 않는다.

### 애플리케이션 내 패킷 캡처

Reliquary Archiver 방식은 정확하고 빠르지만 패킷 캡처 드라이버와 별도 권한이 필요하다. 웹 계산기 자체에 이 기능을 넣기보다는 검증된 외부 도구가 만든 JSON을 업로드받는 편이 현재 프로젝트 범위에 맞다.

## 구현 우선순위

1. UID 공개 프로필 불러오기와 Redis 캐시
2. HSR Scanner JSON 업로드
3. Reliquary Archiver JSON 호환
4. 스크린샷 OCR 실험

이 순서라면 가장 간단한 사용 경험을 먼저 제공하면서, 전체 인벤토리가 필요한 사용자도 수동 입력 없이 사용할 수 있다.

## 구현 결과

2026-09-14에 1단계와 2단계를 구현했다.

- `GET /api/import/uid/{uid}`가 MiHoMo 한국어 파싱 API를 조회하고 5성 장착 유물만 공통 모델로 변환한다.
- UID는 숫자 9자리인지 검증하고 호출자 IP별 분당 10회로 제한하며, 외부 서비스의 404, 429, 시간 초과, 잘못된 응답을 구분해 안내한다. 잘못된 UID 형식은 제한 횟수에 포함하지 않는다.
- MiHoMo 원본 응답은 UID 원문이 드러나지 않는 SHA-256 Redis 키에 5분간 저장한다. Redis가 없어도 외부 조회와 변환은 계속된다.
- `POST /api/import/scanner`가 최대 10MB의 HSR Scanner 버전 4 호환 JSON을 읽는다. 원본 파일은 영구 저장하지 않는다.
- 5성이 아니거나 지원하지 않는 새 스탯을 포함한 유물은 제외하고 이유를 경고 목록에 남긴다.
- 초기 구현에서는 `POST /api/scores/batch`와 Blazor UI를 연결해 가져온 유물을 최대 300개 단위로 계산하고 선택 유물을 수동 입력칸에 적용했다.
- 2026-09-14 후속 개선에서 수동 입력칸과 범용 프로필 선택을 제거했다. 현재는 `POST /api/scores/character-batch`가 선택 캐릭터 ID의 부위별 주옵션, 12개 부옵션 가중치와 정규화 값을 자동 적용하며, 자세한 근거와 구현은 `CHARACTER_RELIC_WEIGHTS.md`에 기록한다.

검증 결과는 다음과 같다.

- MiHoMo 공식 예제 UID `100000999` 실조회: 5성 장착 유물 42개 변환 성공
- Docker와 Redis가 없는 상태: UID 실조회 성공, 캐시 실패는 서버 경고 로그에 기록
- HSR Scanner 버전 4 샘플: 장착 캐릭터, 손 부위, 고정 공격력 주옵션과 부옵션 변환 성공
- Scanner 샘플 일괄 계산: 치명타 프로필 40점 B등급 반환
- 브라우저 초기 검증: UID 42개 표시, 선택 유물 입력 적용, 42개 전체 계산·정렬 확인. 현재 UI는 다시 입력하지 않고 캐릭터 탭 선택 즉시 자동 계산한다.
- 390px 화면: 가로 넘침 없음, 자동 가져오기 컨트롤 1열 배치 확인
- 전체 xUnit 테스트 19개와 Release 빌드: 경고·오류 없이 통과
- 잘못된 Scanner·MiHoMo 필드: `JsonException`으로 정규화해 400·502 응답 경계 유지
- UID 연속 요청: 잘못된 UID 11회는 모두 400이고 제한 횟수를 소비하지 않음. 로컬 MiHoMo 대역 서버로 유효한 요청을 보내 처음 10회는 200, 11번째 요청은 429와 JSON 오류 안내 반환 확인
